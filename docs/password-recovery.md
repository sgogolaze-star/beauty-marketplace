# Password recovery

Sign in links to `/forgot-password`. The server validates the email and requests a Supabase PKCE recovery link with an explicitly trusted callback origin. The response is the same whether an account exists or delivery fails. A short cookie cooldown improves the UI; Supabase Auth owns actual request and delivery rate limits.

Use the default Supabase recovery email's `{{ .ConfirmationURL }}` link. It verifies the email token at Auth and returns a PKCE code to `/auth/callback?flow=recovery`. Open the link in the browser that requested it. The callback supports the SDK's `sb_flow_id` parameter. Do not substitute the signup-only `/auth/confirm?type=email` template for recovery, or configure token-hash recovery templates: direct OTP verification produces a generic OTP authentication method, not the recovery claim required here. Unsupported, expired and used recovery links return a fresh-link form.

`APP_ORIGIN` can specify a verified HTTPS origin. Vercel deployment and branch origins are also trusted automatically; loopback HTTP is allowed locally. An arbitrary request Host/Origin cannot choose where email links go. Supabase's redirect allowlist must independently permit the intended callback URL. Local fixture tests use `http://localhost:3012` consistently because Next's local route redirects normalize the hostname.

The reset page and action require a user verified by Auth plus a recent server-signed `amr.method=recovery` claim, a matching live owned `auth.sessions` row and an unused reset permission. The database atomically consumes that permission before updating the password through Auth. Permission expires 15 minutes after verification; a failed update requires a fresh email link. A regular password sign-in, editable metadata or URL flag cannot unlock the form. Passwords must match and be 8–128 characters. Success requests global sign-out and requires a new sign-in. Revoked refresh sessions do not invalidate already-issued access JWTs before their expiry; the recovery guard separately requires a live session.

`recovery_private.used_sessions` has RLS and no client table grants or policies intentionally. Only identity-checked, explicitly granted functions access it. Supabase's informational “RLS enabled, no policy” advisory reflects this deliberate default-deny table. Passwords and recovery secrets are never stored in application tables or logs.

Verification includes unit tests for validation and trusted origins, desktop/mobile public routes, an optional real-Auth PKCE fixture test, and `tests/db/recovery.sql` for permission isolation, expiry, malformed claims, cross-user sessions, single use and revocation. The optional browser test accepts an ignored JSON file via `BLOOM_RECOVERY_FIXTURES`; its fixture shape is declared in the test. Use disposable accounts and Auth flow/token fixtures only, never customer credentials. No SMTP is used in this fixture test. Clean all fixtures afterward. CI runs the public tests and five transactional database suites; it skips tests requiring live disposable Auth accounts.

As of 28 October 2026, the live public Auth settings endpoint confirms email/password signup is enabled and email confirmation is required. Custom SMTP, inbox delivery, recovery email template and deployed-origin redirect allowlist are unverified: the connector does not expose Auth configuration and the dashboard browser is signed out. Fixture success does not verify email transport. Leaked-password protection remains disabled and must be reviewed before launch.
